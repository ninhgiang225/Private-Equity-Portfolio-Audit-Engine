01   Project Overview

What this pipeline does — and why it matters

Private equity firms and consultants work with company data that arrives in messy, inconsistent formats. A portfolio list might call the same company "Apple Inc.", "AAPL", "Apple Incorporated", and "Aple Corp." — all in the same spreadsheet. Manually reconciling these is slow, error-prone, and doesn't scale.

This pipeline solves that with an automated, end-to-end system: raw company names go in, clean canonical records come out, with every decision traceable and auditable.

02   LangGraph

How LangGraph orchestrates the pipeline

LangGraph is built on top of LangChain and lets you define workflows as a directed graph, where each node is a Python function and edges define the flow between them. The key difference from a plain Python script is that it maintains a shared State object across all nodes — so every stage can read what the previous stage wrote.

Why LangGraph over plain Python?

You could call each stage sequentially in a script. But LangGraph gives you three things a script can't easily provide:

Key advantage

Conditional edges — after the evaluate node, you can branch: records with review-queue items can pause and wait for human input before export runs. This is the "human-in-the-loop" pattern. A script would need you to hardcode this logic; a graph makes it declarative.

src/pipeline/graph.py — StateGraph definition 
from langgraph.graph import StateGraph, END

g = StateGraph(PipelineState)           # State is a TypedDict shared by all nodes

g.add_node("ingest",   ingest_node)       # reads CSV → populates state["records"]
g.add_node("resolve",  resolve_node)      # runs ReAct agent on each record
g.add_node("evaluate", evaluate_node)     # runs LLM judge, fills verdict field
g.add_node("export",   export_node)       # writes to CSV + BigQuery

g.set_entry_point("ingest")
g.add_edge("ingest",  "resolve")
g.add_edge("resolve", "evaluate")

# Conditional: after evaluate, route based on review queue
g.add_conditional_edges(
    "evaluate",
    all_resolved,                          # routing function
    {"export": "export"},               # map return value → next node
)
g.add_edge("export", END)

Understanding PipelineState

State is a TypedDict — a Python dictionary with typed keys. Every node receives the entire state and returns the updated state. This is how information flows through the graph without global variables or class instances.

State schema
class PipelineState(TypedDict):
    input_path:   str                   # set at startup, read by ingest_node
    records:      list[CompanyRecord]    # built by ingest, enriched by resolve+evaluate
    accepted:     list[CompanyRecord]    # filled by evaluate_node
    review_queue: list[CompanyRecord]    # filled by evaluate_node
    rejected:     list[CompanyRecord]    # filled by evaluate_node
    run_id:       str                   # UUID for Langfuse trace grouping
03   ReAct Agent

How the entity resolution agent thinks

ReAct stands for Reasoning + Acting. It's a prompting pattern where the LLM alternates between three steps in a loop until it reaches a final answer:

💭
Thought
The LLM reasons about the current situation: "The name 'Aple Inc' looks like a typo of Apple Inc. I should try fuzzy matching first before using an API call."
🔧
Action
The LLM decides which tool to call and with what arguments: fuzzy_match_tool("Aple Inc")
👁️
Observation
The tool result is fed back to the LLM: "match_found: true, canonical_name: Apple Inc., score: 92". The LLM then decides: stop or keep going.

The three tools and their priority order

The agent's system prompt instructs it to try tools in cost-efficiency order — free and fast first, then API calls only if needed.

PriorityToolWhen usedCost
1stcompany_lookup_toolExact match in canonical DB (case-insensitive)Free — local dict
2ndfuzzy_match_toolHandles typos, abbreviations, word orderFree — RapidFuzz
3rdweb_search_toolUnknown companies not in local DBTavily API call

Why RapidFuzz for fuzzy matching?

RapidFuzz uses token sort ratio — it splits both strings into word tokens, sorts them alphabetically, then computes similarity. This handles word-order variations ("Inc. Apple" vs "Apple Inc.") that simple Levenshtein distance would miss. A threshold of 75/100 was chosen empirically — below that, matches were too unreliable.

src/agent/tools.py — fuzzy match logic
from rapidfuzz import process, fuzz

result = process.extractOne(
    query,                      # "aple inc" (lowercased input)
    candidates,                 # list of known canonical keys
    scorer=fuzz.token_sort_ratio  # handles word-order differences
)
# result = ("apple inc.", 92, 0)  ← (match, score, index)

if result[1] < threshold:       # threshold = 75 by default
    return {"match_found": False}
else:
    return {"canonical_name": entry["canonical"], "similarity_score": result[1]}
Design decision

Tools return JSON strings (not dicts). This is required by the LangChain tool interface — the agent receives tool outputs as text observations in its context window, so they must be serializable.

04   LLM-as-Judge

How the evaluator scores and routes every match

After the resolver agent produces a canonical name, a separate, independent LLM call evaluates the quality of that match. Crucially, the judge uses a different prompt and only sees: the raw input, the resolved output, the domain, and the evidence string. It has no access to the resolver's internal reasoning — this prevents the judge from being biased by the resolver's confidence.

Structured output with Pydantic

The single most important implementation detail: .with_structured_output(MatchVerdict) forces the LLM to return valid JSON that matches the Pydantic schema. No regex parsing, no try/except around JSON loads — if the LLM drifts off-format, LangChain retries automatically.

src/evaluator/judge.py — full evaluator
class MatchVerdict(BaseModel):
    score:     int = Field(description="0–10 match quality", ge=0, le=10)
    rationale: str = Field(description="One sentence explanation")
    verdict:   str = Field(pattern="^(accept|review|reject)$")

# The chain: prompt → LLM with structured output
llm   = ChatOpenAI(model="gpt-4o-mini", temperature=0).with_structured_output(MatchVerdict)
chain = JUDGE_PROMPT | llm

verdict = chain.invoke(
    {"raw_name": raw_name, "resolved_name": resolved_name, ...},
    config={"callbacks": [langfuse_handler]}  # auto-traced by Langfuse
)

Routing thresholds

Three routing zones turn a numeric score into an operational decision:

ScoreVerdictActionRationale
7 – 10 accept Written to BigQuery directly High confidence — agent + judge agree
4 – 6 review Added to review_queue.csv Plausible but uncertain — human verifies
0 – 3 reject Flagged as unresolved Judge disagrees — resolution likely wrong
The human-in-the-loop step

The review_queue.csv is where you become part of the pipeline. In Week 3, you manually label those 20–30 records and compare your labels against the judge's verdict. If the judge is disagreeing with you significantly, you adjust the prompt or thresholds. This is real evaluation data science.

Why temperature=0 for the judge?

Temperature=0 makes the LLM deterministic — the same input always produces the same output. For an evaluator, consistency is more important than creativity. If the judge gave different scores on different runs for the same input, your quality metrics would be meaningless.

05   Langfuse

End-to-end observability — what gets traced and why

Langfuse is an open-source LLM observability platform. It captures traces — hierarchical records of everything that happened during an LLM call — so you can debug failures, monitor costs, and analyze output quality over time.

How traces work in this pipeline

A single company record triggers two LLM calls: one for the resolver agent and one for the judge. Both are linked by the same trace_id, so in the Langfuse dashboard you can see the full story of how one company was processed:

Trace hierarchy in Langfuse
Trace: run_id=abc123 · company_id=42 · raw="Aple Inc"
  ├── Span: resolve:Aple Inc
  │     ├── Tool call: company_lookup_tool("Aple Inc")  → no match
  │     ├── Tool call: fuzzy_match_tool("Aple Inc")     → Apple Inc. (92)
  │     └── LLM output: {canonical: "Apple Inc.", confidence: 0.95}
  │         tokens: 312 input / 48 output  latency: 1.2s
  │
  └── Span: judge:Aple Inc
        └── LLM output: {score: 9, verdict: "accept", rationale: "..."}
            tokens: 280 input / 31 output  latency: 0.8s

What one line of code does

The entire tracing setup requires a single callback handler passed to every chain invocation. Langfuse intercepts LangChain's internal events and logs them automatically:

The only Langfuse code you write
from langfuse.callback import CallbackHandler

handler = CallbackHandler(trace_id="abc123_42", name="resolve:Aple Inc")

chain.invoke(
    {"input": "Aple Inc"},
    config={"callbacks": [handler]}   # ← this is all it takes
)
# Langfuse now has: inputs, outputs, token counts, latency, model name

What you monitor in the Langfuse dashboard

Token cost per run
How many tokens did the resolver vs. judge consume? Is the resolver over-calling web_search (expensive) when fuzzy match would suffice?
Latency per node
Which companies took longest to resolve? Are tickers (like MSFT) slower because the agent needs more tool calls to identify them?
Judge score distribution
Are most scores clustered at 8–9 (good) or spread across the range (inconsistent resolver)? A bimodal distribution suggests the threshold needs calibration.
Error traces
When the agent hits its max_iterations limit or a tool throws an exception, Langfuse captures the full trace so you can debug exactly what went wrong.
06   Data Flow

What happens to each record, step by step

Let's trace a single record — raw_name: "Stipe Inc" (a typo of Stripe Inc.) — through the entire pipeline:

Full record lifecycle
# 1. INGEST — raw CSV row becomes a CompanyRecord
record = {"id": 80, "raw_name": "Stipe Inc", "verdict": "pending", ...}

# 2. RESOLVE — ReAct agent runs
#   Thought: "Stipe Inc — looks like a typo. Try fuzzy match first."
#   Action:  fuzzy_match_tool("Stipe Inc")
#   Observation: {"match_found": true, "canonical_name": "Stripe Inc.",
#                 "domain": "stripe.com", "similarity_score": 82}
#   Thought: "Score 82/100, good enough. Final answer:"
record["canonical_name"] = "Stripe Inc."
record["confidence"]     = 0.82
record["evidence"]       = "Fuzzy matched score 82/100"

# 3. EVALUATE — LLM judge scores the match
#   Prompt: "Raw: Stipe Inc → Resolved: Stripe Inc. (stripe.com)"
#   Output: {score: 7, rationale: "Clear typo, well-known fintech",
#            verdict: "accept"}
record["judge_score"]    = 7
record["verdict"]        = "accept"

# 4. EXPORT — written to BigQuery + resolved_output.csv

BigQuery schema

The final table in BigQuery stores the full audit trail — not just the answer, but every intermediate value. This is what "auditable" means in practice:

ColumnTypeDescription
idINT64Original row ID from input CSV
raw_nameSTRINGThe messy input as received
canonical_nameSTRINGResolved official company name
domainSTRINGCompany domain (apple.com etc.)
confidenceFLOAT64Agent's self-reported confidence 0–1
judge_scoreINT64LLM judge score 0–10
judge_rationaleSTRINGOne-sentence explanation from judge
verdictSTRINGaccept / review / reject
evidenceSTRINGHow the resolution was found
07   Key Design Decisions

Why it was built this way — tradeoffs you should know

What worked well
  • Pydantic structured output eliminated all JSON parsing errors
  • Tool priority order (local first) dramatically reduced API costs
  • Separate judge LLM call made scoring independent and auditable
  • LangGraph state made debugging easy — print state at any node
  • Langfuse callback requires zero boilerplate beyond one import
Known limitations
  • Canonical DB is hand-coded — doesn't scale to 10K+ companies
  • Agent processes serially — slow for large batches without async
  • Judge thresholds (7 / 4) were set manually, not data-driven
  • Web search results are unstructured — LLM parsing can hallucinate
  • No deduplication — same company can appear in multiple rows
If you were doing this at production scale

Replace the hand-coded canonical DB with a vector database (Pinecone, pgvector) so new companies can be added without code changes. Add async batch processing with asyncio.gather() to process 10 companies in parallel. Use Langfuse's dataset feature to formalize your human labels as a reusable eval benchmark.

Conceptual — "explain this to me"
What is LangChain and why did you use it? concept ▾

LangChain is a Python framework that provides standardized abstractions for building LLM-powered applications. Rather than writing raw API calls to OpenAI and manually handling prompts, retries, tool parsing, and output formatting, LangChain gives you composable building blocks: prompts, chains, agents, and tools.

I used it because it handles the hard parts automatically — structured output parsing via Pydantic, tool-call formatting for different LLM providers, and callback hooks that Langfuse uses for observability. Without LangChain, I'd have written hundreds of lines of glue code that would be fragile and hard to test.

Explain LangGraph — how is it different from plain LangChain? concept ▾

LangChain gives you individual components — chains, agents, tools. LangGraph lets you compose them into a directed graph with explicit state management. The key difference is that LangGraph maintains a shared State object across all nodes, so information flows naturally between pipeline stages without global variables or class instances.

It also enables conditional edges — after evaluation, I can branch based on whether the review queue is empty. In a plain Python script, you'd hardcode if/else logic; in LangGraph, routing is declarative and visible in the graph structure. This matters a lot for production workflows where you need human-in-the-loop steps or retry logic.

What is a ReAct agent? Walk me through how it works. concept ▾

ReAct stands for Reasoning + Acting. It's a prompting pattern where the LLM loops through three steps until it has enough information to answer:

  • Thought — the LLM reasons about what it knows and what it needs
  • Action — it calls a tool with specific arguments
  • Observation — it reads the tool output and decides what to do next

In my pipeline, the agent reasons about a messy company name, decides to try fuzzy matching first, reads the score back, and either stops (good match) or tries web search (low score). The loop repeats until it has a confident answer or hits max_iterations=5.

What is LLM-as-judge and what problem does it solve? concept ▾

LLM-as-judge is a quality evaluation pattern where you use one LLM call to score the output of another LLM call. In traditional software, you'd write deterministic tests — but LLM outputs are open-ended text that's hard to test with exact string matching.

In my pipeline, the resolver agent produces a canonical name. Instead of manually checking every result, I send the input and output to a separate judge LLM that scores the match quality 0–10 and provides a rationale. This scales — you can evaluate 100 resolutions automatically in minutes, with structured scores you can aggregate and dashboard. The limitation is the judge can also be wrong, which is why I also did 20 manual labels and compared them.

What is Langfuse and what does it give you that logging doesn't? concept ▾

Langfuse is an LLM observability platform. Plain logging gives you text output — you'd have to write your own parsers and dashboards to make sense of it. Langfuse automatically captures structured traces: inputs, outputs, token counts, latency, model name, and cost for every LLM call.

The critical feature is the hierarchical trace view — you can see that a single company record triggered 2 tool calls + 2 LLM calls, how long each took, and exactly what inputs and outputs each one had. When a resolution fails, you can look at the trace and immediately see: was it the fuzzy match that returned wrong? Did the web search return unhelpful content? Logging alone can't give you that navigable, linked view.

Design choices — "why did you do it this way?"
Why did you use Pydantic for the judge output? Why not parse the JSON yourself? design ▾

Two reasons. First, reliability: LLMs sometimes return malformed JSON, add markdown backticks, or miss a field. Pydantic with .with_structured_output() tells LangChain to enforce the schema — it retries automatically if the output doesn't validate. Manual parsing means I'd need to write that retry logic myself.

Second, field validation: I added ge=0, le=10 constraints on the score field and a regex pattern on verdict. If the LLM returns score=15 or verdict="maybe", Pydantic catches it immediately rather than silently corrupting downstream data. For a QA pipeline, silent data corruption is the worst possible failure mode.

Why did you set the accept threshold at 7 and reject at 4? How would you calibrate those? design ▾

I set them empirically based on the judge's scoring behavior on a small test set — 7+ felt like "clearly right" and below 4 felt like "clearly wrong." But the real answer is: you calibrate them with human labels.

The Week 3 exercise is exactly this: label 20 records yourself, then find the threshold that maximizes agreement between your labels and the judge's verdicts. If you label a record "accept" and the judge gives it a 6, should the threshold be 6 instead of 7? That depends on your risk tolerance — a higher threshold means more human review work but fewer wrong auto-accepts. It's a precision vs. recall tradeoff, and in a PE context, the cost of a wrong entity match is high, so you'd bias toward a higher threshold.

Why fuzzy matching before web search? Why not just always search the web? design ▾

Cost and latency. Web search (Tavily) costs money per call and adds 1–2 seconds of latency. Fuzzy matching is free and runs in milliseconds locally. For a dataset of 100 companies, the difference is small. For 10,000 companies, web search on everything could cost $50+ and take hours vs. seconds for local matching.

In practice, most company name variations — typos, abbreviations, different word order — are resolved correctly by fuzzy matching. Web search is the fallback for genuinely unknown companies not in the local canonical database. This is an automation-first, cost-conscious design decision.

Why use a separate LLM call for the judge instead of asking the resolver to self-score? design ▾

Because self-evaluation is biased. If you ask the same model that produced the answer to score its own answer, it will almost always give itself a high score — this is a well-documented LLM failure mode called sycophancy.

A separate judge call sees only the inputs and outputs, not the internal reasoning chain. This mirrors how peer review works in research — you don't have the author grade their own paper. In practice, using a cheaper model (gpt-4o-mini) for the judge also means the evaluation step adds minimal cost.

Tradeoffs & scaling — "what would you do differently?"
How would you scale this to 10,000 companies? tradeoff ▾

Three main changes:

  • Async processing — replace serial for rec in records with asyncio.gather() to process 20–50 companies concurrently. This alone could reduce runtime 10–20x.
  • Vector database for the canonical store — the hand-coded dict doesn't scale. Embed all canonical names with OpenAI embeddings, store in Pinecone or pgvector, and use semantic similarity search instead of fuzzy string matching. This handles company name paraphrases that RapidFuzz misses.
  • Skip the agent for easy cases — run fuzzy matching on every record first, and only invoke the full ReAct agent for records below the fuzzy threshold. Most "easy" typo cases never need an LLM call at all, which dramatically cuts cost.
What are the failure modes of this pipeline? What could go wrong? tradeoff ▾

Several real failure modes I thought about:

  • Hallucination in web search — the LLM might confidently extract a wrong company name from a web page. The judge catches most of these (low score → review), but not all.
  • Fuzzy match false positives — "Apple Inc." and "Apples Inc." are a 95/100 fuzzy match, but they could be different companies. The judge should catch this with a low score.
  • Agent infinite loop — if tools keep returning "no match," the agent can loop until max_iterations. I handle this with the fallback null return, which triggers a reject verdict.
  • API rate limiting — OpenAI and Tavily have rate limits. Large batches without tenacity retry logic will fail silently mid-run.
  • Schema drift — if the input CSV adds or renames columns, the ingest node breaks. I'd add schema validation at ingest.
How do you measure the accuracy of the pipeline? tradeoff ▾

The dataset has a ground_truth_name column — this lets me compute exact-match accuracy: what percentage of resolved canonical names exactly match the ground truth. I break this down by difficulty tier (easy / medium / hard) and by verdict (did all "accept" records actually resolve correctly?)

A well-calibrated pipeline should have near-100% accuracy on "accept" verdicts — if the judge auto-accepts wrong answers, the thresholds are too low. The dashboard's accuracy section (Week 4) computes this automatically by merging the results with ground truth. In a production setting without ground truth, you'd use the human labels from the review queue as your accuracy signal.

Deep technical — senior engineer might ask
What is token_sort_ratio and why is it better than simple string similarity for company names? deep ▾

Simple Levenshtein distance measures character-level edit distance — it's sensitive to word order. "Apple Inc." vs "Inc. Apple" would score poorly even though they're the same company.

Token sort ratio solves this: it splits both strings into tokens (words), sorts them alphabetically, joins them back, then runs Levenshtein on the sorted versions. So "Apple Inc." → "apple inc" and "Inc. Apple" → "apple inc" become identical after sorting — 100/100 match. For company names where word order varies ("Corp Microsoft" vs "Microsoft Corp"), this is a significant improvement over plain ratio.

Why does the tool return a JSON string instead of a dict? deep ▾

The LangChain ReAct agent places tool outputs into the LLM's context window as text — specifically as "Observation:" strings in the prompt. The context window is pure text, so tool outputs must be serializable strings. A Python dict would be converted via str() which produces ugly, inconsistent formatting.

By returning json.dumps(result) explicitly, I control the exact format the agent sees. The agent is then instructed in its system prompt to parse the JSON observation before acting on it. This is a common pattern in LangChain tool development.

What is the difference between a LangChain Chain and an Agent? deep ▾

A Chain is a fixed sequence of steps — prompt → LLM → output parser. The flow is deterministic and hardcoded. You use chains when you know exactly what steps are needed.

An Agent is dynamic — the LLM itself decides at runtime which tools to call, in what order, and when to stop. It's flexible but less predictable and more expensive. I used an agent for entity resolution because the number of tool calls varies per company: a clean name needs zero LLM calls (just DB lookup), while an unknown ticker might need two tool calls before the agent has enough information. A chain couldn't express this variable branching logic.

Behavioral — "tell me about a challenge"
What was the hardest part of building this project? behavioral ▾

The hardest part was calibrating the judge thresholds. When I first ran the pipeline, I noticed the judge was giving scores of 7–8 to matches I personally would have flagged for review — the agent had resolved "SFDC" to "Salesforce Inc." correctly, but the evidence string was thin, and I wasn't confident. I had to do 20 manual labels, compute where my judgments diverged from the model's, and adjust both the judge prompt and the thresholds.

This was actually the most valuable learning: building an LLM system is not just engineering — it's empirical. You form hypotheses about where it'll fail, generate data to test them, and iterate. The human-in-the-loop step isn't a workaround; it's the ground truth calibration loop that makes the whole system trustworthy.

If you had two more weeks, what would you add? behavioral ▾

Two things with the highest impact:

  • Formalize the eval benchmark in Langfuse — upload my 20 manual labels as a Langfuse Dataset, then run automated eval on every code change. Right now, checking whether my changes improved accuracy is manual. A dataset + automated scorer would make it a one-command check.
  • Async batch processing — the pipeline currently processes companies serially, one at a time. With asyncio.gather() and a semaphore to respect rate limits, I could process 10+ companies in parallel and cut total runtime by 5–10x. This would make the pipeline practical for real PE datasets that often have 500–2000 companies.
